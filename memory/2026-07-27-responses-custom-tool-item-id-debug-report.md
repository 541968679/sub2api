# DEBUG REPORT: Responses custom-tool item ID namespace rejection

- **Symptom:** Production returned HTTP 400: `Invalid 'input[100].id': 'item_643ea17567eacddfb6003ee2'. Expected an ID that begins with 'ctc'.`
- **Root cause:** `input[100]` is a replayed `custom_tool_call`. The Chat Completions -> Responses compatibility bridge generates output item IDs with the generic `generateItemID()` helper (`item_` plus 24 hexadecimal characters), including custom tool calls. On a later tool-continuation turn, `applyCodexOAuthTransformWithOptions()` enables `PreserveReferences`; `filterCodexInputWithOptions()` removes invalid replayed IDs only for `message`, so the custom-tool `item_...` ID is forwarded unchanged. ChatGPT/Codex validates this item type against the `ctc` namespace and rejects the request.
- **Production evidence:** Read-only logs show the failure at `2026-07-27 09:53:03 +08:00` on `/responses`, model `gpt-5.6-sol`, OpenAI OAuth account `1633`, request ID `1f084e4e-be5e-4bf0-9f1e-bcb0534a5bd8`, client request ID `52d4f781-33e3-4c57-8a33-9e26e9f38219`, body size 327,105 bytes. The deployed container was healthy on revision `0a995ef3edc801c4e9a7c93cf7c435de15dfe258`, version `0.1.176`. The same account completed another `gpt-5.6-sol` Responses request with HTTP 200 immediately afterward, excluding account expiry, quota exhaustion, scheduler failure, and general model unavailability.
- **Code evidence:** `backend/internal/pkg/apicompat/chatcompletions_responses_bridge.go` assigns `generateItemID()` to streaming and non-streaming `custom_tool_call` output. `backend/internal/pkg/apicompat/anthropic_to_responses_response.go` defines that helper as 12 random bytes encoded after `item_`, exactly matching the rejected ID shape. `backend/internal/service/openai_tool_continuation.go` classifies custom tool output/tools as continuation signals. `backend/internal/service/openai_codex_transform.go` then preserves IDs in continuation mode but validates only message IDs. The current upstream branch also treats custom tool calls as `fc`, so upgrading alone is not evidence of a complete fix.
- **External evidence:** Public issue `can1357/oh-my-pi#977` reports the same upstream contract and confirms that custom tool replay succeeds when its item ID uses `ctc_` (or when the optional invalid item ID is omitted), while `call_id` continues to pair the call and output.
- **Immediate mitigation:** Start a fresh client conversation or compact/rebuild history without replaying the invalid `custom_tool_call.id`. At the request producer, omit the `id` from replayed custom tool call items, or preserve/generate the proper `ctc_` ID. Rotating accounts, changing quota, retrying the identical body, or remapping the model cannot correct this request shape.
- **Recommended fix:** Make Responses output item ID generation type-aware, at minimum `ctc_` for `custom_tool_call` and `fc_` for `function_call`, in both streaming and non-streaming compatibility bridges. Add a shared defensive sanitizer before OAuth and API-key Responses forwarding that removes item IDs whose namespace does not match their item type rather than fabricating upstream object references. Keep tool pairing on `call_id`. Regression coverage must exercise bridge output followed by a replayed continuation request.
- **Verification performed:** `go test -tags=unit ./internal/service -run 'TestApplyCodexOAuthTransform_CustomAndMCPToolOutputsPreserveCallID|TestFilterCodexInput_StripsInvalidMessageItemIDWhenReferencesPreserved' -count=1 -v` passed. Production access was read-only; no application fix or end-to-end fixed replay was executed because the request was to investigate the cause.
- **Status:** DONE_WITH_CONCERNS. The root cause and immediate mitigation are evidence-backed, but business code remains unfixed and the exact request body was not logged by design, so the precise earlier response that introduced this item cannot be tied to a specific fallback attempt from production logs alone.
